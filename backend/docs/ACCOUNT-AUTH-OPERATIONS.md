# Account administration and authentication operations

## Account management

The authenticated API is rooted at `/api/v1/admin/users`:

- `GET /api/v1/admin/users?q=...` lists accounts. `SUPER_ADMIN` can list all accounts; `CORE_MEMBER` can list student accounts only.
- `POST /api/v1/admin/users` creates an account. `SUPER_ADMIN` can choose supported roles and assign domains; `CORE_MEMBER` can create students only. IDs are generated by the database.
- `PATCH /api/v1/admin/users/{id}` updates account details and active status. Core Members can update students only.
- `PUT /api/v1/admin/users/{id}/roles` changes roles; `SUPER_ADMIN` only.
- `PUT` and `DELETE /api/v1/admin/users/{id}/domains/{domainId}` assign or remove a domain lead; `SUPER_ADMIN` only.
- `POST /api/v1/admin/users/{id}/password-reset` requests a reset email. Core Members can request this for students only.

Setup and reset use `POST /api/v1/auth/password/setup` with `{ "token": "...", "password": "..." }`. The token is random, single-use, expires, and is stored only as a hash. Passwords are BCrypt encoded. Tokens are sent only through the configured mail transport. Administrative actions are written to `audit_logs` without credential or token values. The last active Super Admin cannot be deactivated or removed.

If SMTP is not configured, account creation and reset return `503` and do not expose a link or persist a partial account/reset request.

## Environment configuration

Database defaults in the development profile are `localhost:5433`, database `tech_kernel`, user `tech_kernel`, password `changeme`. Override with `DATABASE_URL`, `DATABASE_USERNAME`, and `DATABASE_PASSWORD`.

Configure outbound mail with:

- `MAIL_ENABLED=true`
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`
- `SMTP_AUTH` and `SMTP_STARTTLS` as appropriate for the provider
- `MAIL_FROM` with a sender accepted by the provider
- `FRONTEND_BASE_URL` set to the public frontend origin

Set `CORS_ALLOWED_ORIGINS` to a comma-separated exact allowlist. Refresh cookies are HttpOnly and scoped to `/api/v1/auth`. In production, `REFRESH_COOKIE_SECURE=true` is the default. Configure `REFRESH_COOKIE_SAME_SITE=Lax` when frontend and API are same-site. For a cross-site deployment use `REFRESH_COOKIE_SAME_SITE=None`, HTTPS, and `REFRESH_COOKIE_SECURE=true`; keep the exact frontend origin in the CORS allowlist. `REFRESH_COOKIE_NAME` can override the cookie name.

The browser keeps access tokens in memory and restores sessions by exchanging the HttpOnly refresh cookie. Login, refresh, logout, and password setup requests must include an allowlisted `Origin`. Refresh tokens are never returned in JSON.

## One-time initial Super Admin bootstrap

The repository includes a dedicated, operator-invoked command for creating `MITTechKernel@mitmumbai.com` as the first Super Admin. It is not a runner or startup hook and is never called by normal application startup. It prompts for the password without terminal echo, requires a 12–128 character password, confirms it, hashes it with the configured BCrypt encoder, and writes an audit record without the password. It refuses if any Super Admin exists or if the requested email is already assigned. PostgreSQL takes a transaction-scoped advisory lock to serialize concurrent attempts.

For local development, run from an interactive terminal in `backend/`:

```sh
KERNEL_INITIAL_ADMIN_BOOTSTRAP=true \
./mvnw -Dspring-boot.run.profiles=dev \
  -Dspring-boot.run.main-class=com.mittechkernel.backend.bootstrap.InitialSuperAdminProvisioningCommand \
  spring-boot:run
```

The command is restricted to the `dev` profile and loopback PostgreSQL at `localhost:5433/tech_kernel`. It explicitly disables Flyway for this command invocation, so the schema must already be initialized through the normal application process. Never pass the password through an environment variable, command argument, shell command substitution, or chat.

For production, first review and apply the migrations using the steps in [the production deployment audit](PRODUCTION-DEPLOYMENT-AUDIT.md). Then run the same dedicated command only after setting `KERNEL_INITIAL_ADMIN_BOOTSTRAP=true` and `KERNEL_INITIAL_ADMIN_PRODUCTION_CONFIRMATION` to the exact `host:port/database` parsed from `DATABASE_URL`, and selecting the `prod` profile. The command rejects localhost, embedded URL credentials, mixed profiles, and any confirmation mismatch. See the audit document for the exact command. The password remains an interactive hidden prompt.


On success, the command prints only the account ID and confirms that no setup token was exposed. Verify by signing in through the configured frontend. Never print or query the stored password hash. Normal application startup does not provision accounts, and the opt-in is required only for the one-off command.

If an administrator already exists, recover that account through its normal authenticated password reset if available. If no administrator can sign in and SMTP is unavailable, have an authorized database operator follow the organization's approved identity-verification and credential-recovery procedure for that existing administrator, recording the action in the audit trail. Bootstrap never creates another administrator, elevates an existing account, or changes the password for an existing email.

An earlier inspection reported an active Super Admin in the local development database. This task intentionally made no database connection, so that status has not been rechecked. The command itself checks current state and will refuse if a Super Admin is present.

## Migrations and local commands

Migrations V15 through V17 add password setup state/tokens and audit storage, case-insensitive email uniqueness, and access-token invalidation after password changes. They are additive; do not edit migrations already applied to an environment. Before applying V16, check for duplicate emails ignoring case and resolve them deliberately.

From the repository root, start the existing local database container if it is stopped, then run:

```sh
cd backend
./mvnw spring-boot:run
```

The frontend runs separately:

```sh
cd frontend
npm install
npm run dev
```

For production, activate the `prod` Spring profile and supply database, JWT, GitHub, CORS, and mail settings through the deployment environment. Never use the development JWT secret or database password in production.
